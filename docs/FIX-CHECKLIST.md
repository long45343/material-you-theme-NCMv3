## 工作项 C:reattach 插入加固(条件项:仅当 A+B 完成后崩溃仍复现)

**目标**:消除"向 React 管理的图标行插入外部节点"这一同族风险。若 B 全部通过则本项**跳过**,只留结论记录。

### C1 决策点:加固方向 ✅ → **选 A:延迟+静默注入**(IconBar 挂载完 + ~500ms 静默后再首次插入;重挂守卫保留)(2026-09-07;条件项,仅当清创后崩溃仍复现时执行)
- **A(推荐)延迟+静默注入**:首次插入等 IconBar 挂载且约 500ms 无相关 DOM 变动(静默期)后再执行;保留重挂守卫。
  - 优:避开 React 初始挂载窗口(首启崩溃的最差时机);改动小,保留现有"插入图标行"的布局正确性。
  - 劣:按钮出现晚几百 ms;静默期阈值需要试。
- **B fixed 覆盖层**:按钮完全不进 React 行,JS 只读坐标(getBoundingClientRect)写 CSS 变量,`position:fixed` 摆放。
  - 优:与 React 树零结构接触,根治该类问题。
  - 劣:窗口缩放/切页需重算,实现最复杂;与 D 项若同选 fixed 需统一坐标更新逻辑。
- **C 单次插入不重插**:插一次,React 抹掉就放弃。
  - 优:干扰最小。
  - 劣:徽章数一变按钮就消失——等于回到老 bug,基本不可接受,列出仅为完整。

## 工作项 D:BNCM 归位(E3-B 纯 CSS,修 bug#2)

**目标**:把 chromatic 音符按钮对齐到图标行高度(✉ ⚙ [我们] [BNCM]),**严禁 JS 搬移/插入 React 节点**(HANDOFF 明确禁令),只允许读坐标 + CSS 定位。

### 操作步骤(选项确定后细化)
1. ⬜ 按 D1 所选路线实现;
2. ⬜ 先解决探针 miss:用 `title="BetterNCM"` 遍历搜索拿到按钮节点(00:53 两次探针均 miss);
3. ⬜ 构建部署后目视验证对齐(截图对比 ✉/⚙ 基线);
4. ⬜ 验证窗口缩放、徽章数量变化后仍对齐(D1-B/C 路线尤其需要)。

### D1 决策点:技术路线 ✅ → **选 A:只读探针 + CSS 变量定位**(getBoundingClientRect 只读 → --bncm-* 变量 → position:fixed;resize/MutationObserver 重算;绝不搬移/插入 React 节点)(2026-09-07)
- **A(推荐)只读探针 + CSS 变量定位**:JS 仅 `getBoundingClientRect` **读**音符按钮 rect(只读不搬,React 安全)→ 写 `--bncm-*` CSS 变量 → 音符按钮用 `position:fixed` 对齐图标行基线;resize + MutationObserver 触发重算。JS 侧不插入、不搬移、不删除任何 React 节点。
  - 优:纯显示层干预,规避 React 协调冲突;对窗口尺寸、徽章数量变化自适应。
  - 劣:比纯 CSS 多一层 JS;rect 获取需先解决探针 miss;fixed 元素脱离文档流,父容器滚动/布局变化时要保证重算覆盖全(需实测)。
- **B 纯静态 CSS**:按窗口右上角估算位置写死。
  - 优:零 JS,最简单。
  - 劣:窗口尺寸、徽章数量(网易云会动态加徽章,这正是 6d91769 修过的问题)一变就错位;探针至今 miss 也说明其原生位置不固定,大概率不准。
- **C 替身按钮**:隐藏原生入口,自建按钮转发调 chromatic 的打开接口。
  - 优:位置完全可控、最稳。
  - 劣:依赖 chromatic 内部 API(版本升级易碎);点击链路要逆向;工作量大,超出"E3-B 纯 CSS"的范围。

### D2 决策点:上车节奏 ✅ → **选 A:两轮发布**(本轮清创+验证;通过后下一轮单独上 BNCM 归位)(2026-09-07)
- **A(推荐)两轮发布**:本轮只发清创版(A 项)+ 回归验证(B 项);全部通过后下一轮单独上 BNCM 归位(D 项)。
  - 优:变量隔离——若清创版仍崩溃,可确定与新增定位逻辑无关;每轮 diff 小,回滚容易。
  - 劣:多一次部署与验证周期。
- **B 一轮打包**:清创 + 归位同一构建发布。
  - 优:省一轮部署/验证。
  - 劣:若发布后崩溃复现,无法区分是"清创不彻底"还是"新定位逻辑引入",bug#3 的归因被污染。
